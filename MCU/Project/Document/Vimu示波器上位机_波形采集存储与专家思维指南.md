# Vimu 示波器上位机：波形采集、存储与工程判断指南

> 适用场景：Windows 7 工控机 + Qt/C++ 上位机 + Vimu MSO 示波器/采集卡 + STM32 执行器控制板  
> 依据资料：用户提供的《上位机功能需求》与《Vimu C SDK 使用指南 V1.22（2026-01-20）》  
> 说明：SDK 文档给出了采集 API、普通 Capture、Stream 流模式、原始 ADC / 电压数据读取、触发和回调机制，但没有明确当前具体硬件型号的最高采样率、ADC 位数和模拟带宽。因此本文中的容量计算给出通用公式和典型示例；最终参数必须以实际设备 `GetOscSupportSampleRates()`、`GetMemoryLength()` 和硬件规格为准。

---

## 1. 先给结论：这个项目推荐的采集方案

本项目不建议“所有时间都按最高采样率连续保存”。

更合理的是采用 **两条采集路径**：

### 1.1 实时观察模式：Stream + 环形缓存

用途：

- 操作人员实时看 CH1~CH4 波形
- 调试执行器
- 检查信号是否正常
- 不要求永久保存全部数据

建议：

```text
Vimu Stream Callback
        ↓
快速复制 SDK buffer
        ↓
采集线程 / 数据队列
        ↓
Ring Buffer（例如保留最近 5~10 秒）
        ↓
显示降采样
        ↓
Qt UI 20~30 FPS
```

关键原则：

- SDK 回调中只做“快速复制 + 入队”，不要绘图、写数据库、生成报告。
- 采集速度和 UI 刷新速度必须解耦。
- UI 不需要把每个 ADC 点都画出来。
- 实时模式默认不永久保存所有原始数据；只有用户点击“保存”或自动测试触发后才落盘。

Vimu SDK 明确提供流模式 `StreamCapture()`、`SetStreamDataReadyCallBack()`，并特别提醒回调函数不能处理复杂任务，否则可能导致缓冲堆积或触发硬件看门狗重连。

---

### 1.2 自动检测模式：Trigger/Capture + 固定时间窗保存

车辆执行器检测更适合：

```text
STM32 下发目标开度
        ↓
执行器开始动作
        ↓
等待指定条件 / 触发
        ↓
Vimu Capture
        ↓
采集固定时间窗
        ↓
读取 CH1~CH4
        ↓
读取 STM32 实际开度 / 传感器
        ↓
OK / NG
        ↓
保存本次原始波形 + 元数据 + 结果
```

这种方案比“连续录制几个小时再找检测点”更可靠、容量也小很多。

推荐每个测试步骤保存：

- 触发前数据：Pre-trigger（如果硬件型号支持）
- 动作过程
- 动作完成后的稳定区
- STM32 指令时间
- STM32 反馈时间
- 示波器触发位置
- 实际采样率
- 每通道量程
- 原始 ADC 数据

---

## 2. 采样频率到底怎么定义

波形系统里最容易混淆的是“频率”。

至少要区分 5 个不同概念：

| 名称 | 含义 | 示例 |
|---|---|---|
| 模拟带宽 | 示波器前端能有效通过的频率范围 | 20 MHz |
| ADC 采样率 | 每秒真正采多少个点 | 1 MS/s |
| 采集时间窗 | 一次 Capture 保存多长时间 | 500 ms |
| UI 刷新率 | 屏幕一秒刷新多少帧 | 20 FPS |
| 自动测试频率 | 执行器多久执行一次测试步骤 | 1 次/2 s |

这五个参数不能混为一谈。

### 2.1 采样率的理论底线

如果被测信号最高有效频率为 `B`：

```text
Fs > 2 × B
```

这是奈奎斯特条件的理论底线。

但工程上如果要“看清波形形状”，通常不会只取 2 倍。

常见经验：

```text
一般周期波形：
Fs ≈ 5~10 × 最高有效频率

希望看清边沿、脉冲形状：
Fs 往往需要更高，
并结合信号上升时间决定。
```

例如被测有效信号主要在 10 kHz 内：

```text
最低理论值：>20 kS/s
工程上可从：100 kS/s 左右开始验证
```

不是因为“100 kS/s 是标准答案”，而是要在波形保真度和数据量之间找平衡。

---

### 2.2 对执行器项目，更应该从“信号特征”反推采样率

需要先回答：

1. 采集的是直流位置电压，还是 PWM？
2. PWM 频率是多少？
3. 是否要看电机换向瞬态？
4. 是否要看毛刺？
5. 是否需要测上升时间/下降时间？
6. 是否只判断稳定值？
7. 信号中最高有意义的频率是多少？

例如：

#### 场景 A：只检测缓慢变化的位置传感器

信号变化速度可能只有几十 Hz。

100 kS/s 可能已经非常富余。

#### 场景 B：需要观察 20 kHz PWM

如果要看 PWM 的占空比和基本波形：

```text
200 kS/s 只是约 10 点/周期
```

如果还要观察边沿、纹波和异常尖峰，通常需要更高采样率。

#### 场景 C：要抓短毛刺

不能只看 PWM 基频。

真正决定采样率的可能是：

```text
毛刺宽度
上升时间
下降时间
```

因此最终采样率应由真实执行器信号实测后确定，而不是直接把设备设置成最高档。

## 3. 本项目建议把采样率做成“模板参数”

不要把采样率写死在代码里。

测试模板应包含：

```json
{
  "oscilloscope": {
    "sample_rate": 1000000,
    "capture_duration_ms": 500,
    "channels": [1, 2, 3, 4],
    "pre_trigger_percent": 20
  }
}
```

不同执行器允许不同采样策略：

```text
执行器 A：100 kS/s，500 ms
执行器 B：1 MS/s，200 ms
执行器 C：5 MS/s，50 ms
```

启动软件后应使用 Vimu SDK 查询实际支持值：

```cpp
GetOscSupportSampleRateNum();
GetOscSupportSampleRates();
SetOscSampleRate();
```

因此软件中的下拉框最好显示“硬件真实支持的采样率”，而不是自己写死一组不存在的档位。

# 4. 波形保存什么数据结构最合理

## 4.1 不建议直接把全部波形写进 SQLite

SQLite 适合保存：

- Test ID
- 型号
- 序列号
- 测试时间
- 目标开度
- 实际开度
- 传感器值
- OK/NG
- 波形文件路径
- 报告路径

不建议长期把数百万、数千万个 ADC 点作为大量数据库行保存。

例如不要设计成：

```text
waveform_points
--------------------------------
test_id
channel
sample_index
voltage
```

如果 4 通道 × 1,000,000 点：

```text
一次测试就是 400 万行
```

这会使：

- 插入很慢
- 查询很慢
- 数据库迅速膨胀
- 备份困难

# 5. 推荐的数据分层

推荐：

```text
SQLite：管理“索引和业务数据”
文件系统：管理“波形大数据”
```

例如：

```text
data/
└── 2026/
    └── 08/
        └── 15/
            └── TEST_20260815_000123/
                ├── meta.json
                ├── waveform.bin
                ├── preview.png
                └── report.pdf
```

SQLite：

```text
test_record
├── test_id
├── actuator_model
├── serial_number
├── start_time
├── result
├── waveform_path
├── preview_path
└── report_path
```

这样历史查询快，波形文件也容易搬运、备份和归档。

# 6. 波形文件应该存 double 还是原始 ADC

Vimu SDK 提供两种读取路径：

```cpp
ReadVoltageDatas()
```

可以直接得到 `double` 电压值。

也可以：

```cpp
ReadADCDatas()
ReadADCToVoltageZoom()
ReadADCToVoltageBias()
```

保存原始 ADC，并通过：

```text
Voltage = ADC × Zoom + Bias
```

恢复为电压。

## 推荐结论

**正式产品优先保存原始 ADC + 标定参数，而不是保存 double 数组。**

原因：

### 原始 ADC 的优势

- 数据最接近采集源
- 占用空间小
- 后期可以重新计算电压
- 可以修改滤波算法后重新分析
- 能保留“当时真实 ADC Code”
- 方便追溯

如果硬件是：

```text
8-bit ADC
```

一个点：

```text
1 Byte
```

如果是：

```text
12-bit ADC
```

工程中通常用：

```text
uint16_t
```

保存，即：

```text
2 Bytes / Sample
```

而 `double`：

```text
8 Bytes / Sample
```

空间会大很多。

# 7. 推荐 waveform.bin 格式

建议定义自己的版本化二进制格式，例如：

```text
+-------------------------------+
| File Header                   |
+-------------------------------+
| CH1 Raw Samples               |
+-------------------------------+
| CH2 Raw Samples               |
+-------------------------------+
| CH3 Raw Samples               |
+-------------------------------+
| CH4 Raw Samples               |
+-------------------------------+
| Optional CRC                  |
+-------------------------------+
```

Header 建议至少包含：

```cpp
struct WaveHeader
{
    char magic[8];              // "VMWAVE01"
    uint32_t version;

    uint64_t test_id;
    int64_t timestamp_us;

    uint32_t sample_rate;
    uint32_t sample_count;
    uint32_t channel_mask;

    uint16_t adc_bits;
    uint16_t bytes_per_sample;

    double trigger_position;

    double zoom[4];
    double bias[4];

    int32_t range_min_mv[4];
    int32_t range_max_mv[4];

    uint32_t data_crc32;
};
```

重点不是这个结构必须一模一样，而是：

> **波形数据一定要自描述、带版本号、带实际采集参数。**

否则两年以后软件升级，很可能已经不知道一个 `.bin` 文件应该怎么解释。

# 8. 每个通道单独文件还是一个文件

两种都可以。

## 方案 A：每个通道一个文件

```text
ch1.bin
ch2.bin
ch3.bin
ch4.bin
```

优点：

- 简单
- 某通道单独读取方便

缺点：

- 文件数量非常多
- 数据和元数据一致性更难管理

## 方案 B：一次测试一个容器文件

```text
waveform.bin
```

内部包含 4 通道。

优点：

- 一次测试只有一个波形文件
- 不容易缺某一路
- 归档方便
- 报告关联方便

**本项目更推荐方案 B。**

# 9. 连续存储空间怎么算

核心公式：

```text
数据量 = 采样率 × 通道数 × 每点字节数 × 时间
```

例如：

```text
Fs = 1 MS/s
4 通道
uint16 = 2 Byte
```

则：

```text
1,000,000 × 4 × 2
= 8,000,000 Byte/s
≈ 8 MB/s
```

所以：

```text
1 分钟 ≈ 480 MB
1 小时 ≈ 28.8 GB
24 小时 ≈ 691.2 GB
```

这就是为什么正式检测软件通常不会全天候保存所有原始高速采样点。

---

# 10. 4 通道连续数据容量示例

以下使用十进制 MB/GB，未计算文件头、索引等少量开销。

## 使用 16-bit 容器保存原始 ADC

| 每通道采样率 | 4通道数据率 | 1分钟 | 1小时 |
|---:|---:|---:|---:|
| 10 kS/s | 80 KB/s | 4.8 MB | 288 MB |
| 100 kS/s | 0.8 MB/s | 48 MB | 2.88 GB |
| 1 MS/s | 8 MB/s | 480 MB | 28.8 GB |
| 5 MS/s | 40 MB/s | 2.4 GB | 144 GB |
| 10 MS/s | 80 MB/s | 4.8 GB | 288 GB |

---

## 如果直接保存 double

4 通道、1 MS/s：

```text
1,000,000 × 4 × 8
= 32 MB/s
```

即：

```text
1 分钟 ≈ 1.92 GB
1 小时 ≈ 115.2 GB
```

所以“为了编程方便全部保存 double”在长期数据保存上代价很高。

# 11. 对本项目更有意义的是“单次测试容量”

例如：

```text
4 通道
1 MS/s
uint16
采集 100 ms
```

单次：

```text
1,000,000 × 0.1 × 4 × 2
= 800,000 Byte
≈ 0.8 MB
```

1000 次：

```text
≈ 800 MB
```

如果每次采集 500 ms：

```text
≈ 4 MB / 次
1000 次 ≈ 4 GB
```

这个容量对于工业检测设备就合理得多。

# 13. 五个最核心的专家思维模式

严格说，不存在“所有专家 100% 都认同”的五条。  
但在示波器、DAQ、工业测试系统中，下面五个思维模式基本属于非常广泛的工程共识。

---

## 思维模式 1：先看信号带宽，再谈采样率

初学者：

> 设备最高 100 MS/s，我就用 100 MS/s。

专家：

> 我要测什么现象？它的最高有效带宽和最快边沿是多少？

真正的链路是：

```text
被测信号
↓
探头
↓
模拟前端
↓
抗混叠
↓
ADC
↓
数字处理
↓
显示
```

如果模拟前端只有某个带宽，单纯无限提高 ADC 采样率不会凭空增加真实信息。

---

## 思维模式 2：时间、采样率、通道数、空间是一个乘法问题

专家看到需求后会立刻估算：

```text
Fs × Time × Channels × Bytes/Sample
```

任何一个参数增加 10 倍：

```text
数据吞吐和容量基本也增加 10 倍。
```

这也是采集软件必须做容量预算的原因。

---

## 思维模式 3：采集链路和显示链路必须解耦

错误架构：

```text
SDK Callback
↓
直接画 Qt 曲线
↓
直接写 SQLite
↓
直接生成统计
```

结果往往是：

- UI 卡顿
- Callback 阻塞
- Buffer 堆积
- USB 掉线
- 看门狗重启

专家通常设计：

```text
硬件采集
↓
快速复制
↓
Queue / Ring Buffer
↓
处理线程
├── 存储
├── 判定
└── 显示降采样
```

---

## 思维模式 4：保存“原始事实”，展示“派生结果”

原始 ADC 是事实数据。

下面这些通常属于派生数据：

- 电压值
- 滤波后的波形
- RMS
- 峰峰值
- 平均值
- OK/NG
- 缩略波形

因此重要工业数据最好保存：

```text
原始 ADC
+
采样参数
+
标定参数
+
触发信息
```

以后算法修改，还能重新计算。

---

## 思维模式 5：可追溯性比“画得漂亮”更重要

工业检测最重要的问题往往不是：

> 当时屏幕上是什么样？

而是：

> 半年前这一台产品为什么被判 NG？

所以必须能够回答：

- 使用了哪个模板？
- 软件版本是什么？
- 采样率是多少？
- 量程是多少？
- 原始波形是什么？
- STM32 当时返回了什么？
- 判定规则是什么？
- 谁、何时执行的测试？

因此：

```text
Raw Data + Metadata + Version + Result
```

应该作为一个完整测试记录存在。

# 14. 专家之间争议最大的三个问题

下面不是“整个行业只有这三个争议”，而是和本项目最相关、也最常见的三组硬核争论。

---

## 争议 1：连续流式保存 vs 触发式分段保存

### A 方：连续 Stream 全保存

核心论据：

> 只有连续原始数据才能保证未知异常不会被漏掉。

优势：

- 不依赖触发条件
- 可以事后回看
- 可以发现意料之外的异常
- 适合研发、故障复现

最硬核的一点：

> 如果异常发生在你的 Capture 窗口之外，这个事件从数据上等于从未发生。

---

### B 方：Trigger/Capture 分段保存

核心论据：

> 工业检测的目标不是当数据录像机，而是对确定测试动作做可重复检测。

优势：

- 数据量小很多
- 测试记录和动作天然对应
- 报告容易生成
- 存储寿命更长
- 网络/磁盘吞吐要求低
- 更容易做 OK/NG

最硬核的一点：

> 连续保存制造了大量“没有业务价值的数据”，却显著增加系统失败面。

---

### 本项目推荐

**混合方案：**

```text
实时：Stream + Ring Buffer，不默认永久保存

自动测试：
Trigger/Capture + 原始数据永久保存

发现 NG：
可额外把故障前后 Ring Buffer 一并保存
```

这是最适合车辆执行器检测的方案。

---

# 15. 争议 2：保存原始 ADC vs 保存转换后的浮点电压

## A 方：保存 Raw ADC

论据：

- 最接近原始采集事实
- 容量小
- 可以未来重算
- 保留 ADC 码
- 便于算法迭代
- 适合计量追溯

例如：

```text
12-bit ADC → uint16_t
2 Byte/sample
```

---

## B 方：直接保存 Voltage double/float

论据：

- 文件拿出来就能分析
- 不依赖后续 Zoom/Bias
- Python/MATLAB/Excel 更容易使用
- 文件语义直观

---

## 真正的问题

如果只保存 ADC，却丢失：

```text
Zoom
Bias
Range
ADC Bits
版本
```

Raw 可能无法正确恢复。

如果只保存 double：

- 容量显著增加
- 原始 ADC code 不再存在
- 校准算法更新后不能重新从最原始码重建

---

### 本项目推荐

保存：

```text
Raw ADC
+
Zoom
+
Bias
+
Range
+
Sample Rate
+
ADC Bits
```

需要第三方分析时，再导出：

```text
CSV / float
```

而不是把 double 作为主归档格式。

---

# 16. 争议 3：采样率越高越好 vs 只采“足够”的数据

## A 方：尽量高采样率

论据：

- 时间分辨率更高
- 更容易看到短毛刺
- 边沿细节更丰富
- 后期可以数字滤波/降采样
- 未知异常更不容易漏掉

最硬核论据：

> 数据没采到，后期永远无法恢复。

---

## B 方：采样率应该“足够即可”

论据：

- 模拟带宽才是信息上限的重要约束
- 无限过采样不会无限增加有效信息
- 高采样率增加：
  - USB 带宽
  - 内存
  - CPU
  - SSD 写入
  - 文件容量
  - 数据处理延迟
- 大量冗余数据可能反而降低系统稳定性

最硬核论据：

> 工业测试系统追求的是可靠检测，不是追求最大数字。

---

### 本项目推荐

研发阶段：

```text
可以高采样率探索信号
```

量产检测阶段：

```text
根据实际信号，
确定足以稳定判定的最低合理采样率，
再留一定裕量。
```

这样能兼顾质量与稳定性。

# 17. 十个能快速看出一个人是否真的懂的面试/评审问题

## 问题 1

**示波器“100 MHz 带宽”和“100 MS/s 采样率”有什么区别？为什么不能当成同一个参数？**

真正懂的人应该谈到：

- 模拟前端带宽
- ADC 采样时间分辨率
- Nyquist
- 波形保真度
- 二者互相影响但不等价

---

## 问题 2

**4 通道、1 MS/s、16-bit 保存，连续采 1 小时大约多少数据？**

正确量级：

```text
1M × 4 × 2 × 3600
≈ 28.8 GB
```

如果连数量级都算不出来，通常没有真正做过高速采集系统。

---

## 问题 3

**为什么 Vimu SDK Callback 里不应该直接画波形和写磁盘？**

深入回答应该出现：

- SDK 工作线程
- Callback 阻塞
- Watchdog
- Buffer 堆积
- Backpressure
- UI 线程安全
- 数据拷贝和消息队列

---

## 问题 4

**如果屏幕宽度只有 1920 像素，但一次采到 1,000,000 个点，你准备怎么画？**

真正懂的人通常不会说：

> 把 100 万点全部 QPainter 画出来。

而会讨论：

- Decimation
- Min/Max Envelope
- LTTB 等降采样
- zoom level
- 原始数据和显示数据分离

特别是毛刺检测场景，简单“每 N 点取一个”可能把尖峰直接丢掉。

---

## 问题 5

**为什么波形保存建议保存 Raw ADC + Zoom/Bias，而不是只保存截图？**

应该谈到：

- 可追溯
- 可重新分析
- 算法升级
- 缩放测量
- 截图不是原始数据
- 标定参数

---

## 问题 6

**20 kHz PWM 应该设置多少采样率？**

这里没有一个固定标准答案。

真正懂的人会反问：

- 只测频率还是占空比？
- 要不要看边沿？
- 最短脉宽是多少？
- 上升时间多少？
- 是否要看毛刺？
- 示波器模拟带宽多少？

如果直接回答：

> 40 kS/s，因为 Nyquist。

通常说明理解只停留在公式层面。

---

## 问题 7

**STM32 发出“50% 开度”命令后，示波器应该什么时候 Capture？**

真正的回答应该讨论同步策略：

- 命令发送时间
- ACK 时间
- 电机开始动作时间
- 外部触发
- GPIO Trigger
- Pre-trigger
- 固定 delay 的误差
- STM32 时间戳
- 软件 USB 延迟

---

## 问题 8

**如果 Stream 数据处理速度低于硬件产生速度，会发生什么？应该怎么处理？**

深入回答应该包含：

```text
Queue 增长
↓
内存增长
↓
延迟越来越大
↓
最终丢数据 / OOM / SDK Buffer 堆积
```

解决方法：

- 有界队列
- Ring Buffer
- 丢弃显示数据
- 降采样
- 批量写盘
- 流量监控
- backpressure 策略

---

## 问题 9

**为什么 SQLite 里不建议“一行存一个采样点”？**

应该能从：

- 行数
- 索引
- transaction
- write amplification
- 查询性能
- 文件尺寸

解释。

合理回答：

```text
SQLite 保存元数据和索引
二进制文件保存 bulk waveform
```

---

## 问题 10

**如果半年后客户说某个 NG 判错了，你需要保存哪些东西才能真正复现？**

真正深入的人至少会提到：

- Raw ADC
- Sample Rate
- Range
- Zoom/Bias
- Trigger
- 测试模板版本
- 软件版本
- STM32 固件版本
- STM32 原始反馈
- 目标指令
- 判定上下限
- 时间戳
- 设备 ID

这个问题非常能区分“做过产品”和“只会写界面”的人。

# 18. 最终总结

对于当前 Vimu + STM32 执行器检测项目，建议形成下面的标准架构：

```text
                    ┌───────────────┐
                    │ Vimu Hardware │
                    └───────┬───────┘
                            │ USB
                            ↓
                    ┌───────────────┐
                    │  Vimu SDK DLL │
                    └───────┬───────┘
                            │ Callback
                            ↓
                     快速复制 Buffer
                            ↓
                    ┌───────────────┐
                    │ Ring / Queue  │
                    └───────┬───────┘
                 ┌──────────┼──────────┐
                 ↓          ↓          ↓
              UI降采样    自动判定     文件保存
              20~30FPS                 Raw ADC
                 │                      +
                 │                   Metadata
                 ↓
             实时波形
```

数据保存：

```text
SQLite
    ↓
保存业务记录 / 索引

waveform.bin
    ↓
保存 Raw ADC + Header

preview.png
    ↓
快速历史预览

report.pdf
    ↓
正式检测报告
```

采集策略：

```text
实时观察
    ↓
Stream + Ring Buffer
    ↓
默认不全量永久保存

正式检测
    ↓
Trigger/Capture
    ↓
固定时间窗口
    ↓
Raw ADC 永久保存
```

容量规划始终使用：

```text
Fs × Channels × BytesPerSample × Time
```

作为第一原则。

# 19. 项目落地前必须确认的参数

在正式冻结波形数据格式和磁盘容量之前，还需要确认：

1. 当前 Vimu **具体硬件型号**
2. 实际 ADC 位数：8-bit / 12-bit / 其他
3. 最高模拟带宽
4. 硬件实际支持的 Sample Rate 列表
5. 4 通道同时开启时最高 Sample Rate 是否下降
6. 实际 Memory Depth
7. Stream 模式下 4 通道最大持续吞吐
8. 执行器信号最高有效频率
9. PWM 频率及最短脉宽
10. 一次自动测试需要保存多长时间
11. 一天预计测试多少台/多少循环
12. 原始波形要求保存多久

拿到这些参数后，可以精确反推出：

```text
每天产生多少 GB
一个月需要多少 SSD
是否需要压缩
数据保存期限
SSD 容量和寿命要求
```

## 一句话设计原则

> **不要把示波器上位机设计成“不断产生 double 数组并全部存盘的软件”，而应该设计成“以原始数据为证据、以元数据保证可追溯、以触发窗口控制数据规模、以流式缓存服务实时显示”的工业检测系统。**
